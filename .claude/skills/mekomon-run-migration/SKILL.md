# הרצת מיגרציה במופעי המקומונים

מיגרציות **מוחרגות מהסנכרון האוטומטי** ואינן רצות מעצמן. כשקלוד צריך
שמיגרציה תרוץ, הוא לא שולח את חיים לחפש — הוא מגיש לו הכל מוכן, לפי
הפורמט הזה, מופע-מופע.

## הפורמט המחייב — לכל הרצה

לכל מופע שצריך את ההרצה, בלוק אחד:

1. **קישור ישיר** ל-SQL Editor של המופע (פותח ישר עורך ריק):
   `https://supabase.com/dashboard/project/<ref>/sql/new`
2. **הטקסט המלא להעתקה** — תוכן ה-SQL בבלוק קוד אחד שלם (לא קטעים,
   לא "ראה קובץ"). חיים מעתיק → מדביק → Run. זהו.
3. משפט אחד: מה המיגרציה עושה ולמה, בעברית פשוטה בלי ז'רגון.

אחרי שחיים כותב שהריץ ("רץ", "בוצע", "הרצתי") — ממשיכים בזרימה שנחסמה
(למשל מיזוג ה-PR שהמתין למיגרציה).

## כללים

- כל מיגרציה חייבת להיות **idempotent** (בטוחה להרצה חוזרת) — ואם היא
  כזו, לכתוב זאת ליד הבלוק כדי שחיים לא יחשוש להריץ שוב.
- SQL שנוגע במדיניות אבטחה (RLS/storage/policies): לוודא שהוא זהה לגרסה
  העדכנית ביותר בתבנית — לעולם לא להגיש גרסה ישנה שמחלישה תיקון קיים.
- אם קיים בסביבה `SUPABASE_ACCESS_TOKEN` (או `SUPABASE_DB_URL`): להציע
  להריץ ישירות במקום ידנית, ולהריץ רק אחרי אישור של חיים. גם אז — להראות
  לו קודם את ה-SQL שירוץ.
- הרצת SQL היא שינוי מסד נתונים; לעולם לא מריצים DELETE/UPDATE על נתונים
  עסקיים דרך הזרימה הזו בלי אישור מפורש ונפרד.
